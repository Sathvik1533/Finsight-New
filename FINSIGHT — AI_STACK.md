## 1. AI Philosophy

### 1.1 The Problem with AI-First Financial Systems

Most financial AI products fail for the same reason: they ask language models to do
work that language models are bad at. Computing totals. Calculating percentages.
Detecting whether two numbers are within 10% of each other. These are not reasoning
tasks — they are arithmetic tasks. Language models are probabilistic text generators.
Asking a language model to compute your tax liability is like asking a calculator to
explain why your spending is emotional.

FinSight is built on a different premise: **AI does what only AI can do. Python does
everything else.**

### 1.2 The Deterministic-First Contract

Every capability in FinSight is first evaluated against this question:

> *Can this be computed deterministically from the available data?*

If yes: Python. If no: AI.

```
┌─────────────────────────────────────────────────────────────────────┐
│                    DETERMINISTIC LAYER (Python + SQL)               │
│                                                                     │
│  ✓ Tax liability = SUM(business transactions) × 0.30               │
│  ✓ Subscription detected = same merchant ± 3 days, amount ± 10%    │
│  ✓ Budget leakage = current month > 3-month baseline × 1.35        │
│  ✓ Intelligence level = CASE WHEN receipt_count >= 10 THEN 4 ...   │
│  ✓ Health score sub-components (consistency, diversification)       │
│  ✓ Category spend breakdown = GROUP BY category SUM(amount)         │
│  ✓ Anomaly flag = deviation > 2.5 standard deviations from mean    │
│  ✓ Weekend vs weekday ratio = SQL date functions                    │
│                                                                     │
├─────────────────────────────────────────────────────────────────────┤
│                    AI LANGUAGE LAYER (NVIDIA + Groq + Gemini)       │
│                                                                     │
│  ✓ Read degraded text from a thermal receipt photograph (NVIDIA)   │
│  ✓ Determine that "AMZN Mktp" means Shopping & Retail (Groq)       │
│  ✓ Explain that a 40% food spend increase is notable (Gemini)      │
│  ✓ Synthesize: "Your subscriptions cost ₹3,400/mo" (Gemini)        │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### 1.3 Why This Separation Matters

**Auditability.** When a user's tax estimate is wrong, the bug is in a Python function —
not somewhere inside a 70B parameter model. It can be found, fixed, and traced.

**Trust.** Users making financial decisions need to trust the numbers. "Computed from your
transactions using SQL" is trustworthy. "Generated by a language model" is not, for numbers.

**Cost.** Every AI call costs money. Deterministic computation costs CPU cycles. At 10,000
users uploading an average of 15 receipts/month, the difference between calling Gemini for
every computation vs. only for language tasks is the difference between a $1,200/month AI
bill and a $116/month AI bill.

**Hallucination surface.** The more numerical work you give a language model, the larger
the surface area for hallucination. FinSight's AI models receive pre-computed numbers as
facts — they cannot invent numbers that were never in the prompt.

### 1.4 What "AI Only for Interpretation" Means in Practice

```
NOT THIS (AI computes):
  Prompt: "Here are 47 transactions. What is my total food spend this month?"
  Risk: Model says ₹8,230. Real answer is ₹8,047. Nobody catches it.

THIS (Python computes, AI interprets):
  Python: food_total = 8047.00  ← computed, verified, written to DB
  Prompt: "Food spend this month: ₹8,047 (38% of total). Describe this pattern."
  Risk: Model may mis-describe, but cannot mis-compute.
```

This is not a theoretical concern. In internal testing of V1 (Gemini-only pipeline),
Gemini computed transaction totals incorrectly in 3.2% of cases — always within plausible
range, always undetectable without ground-truth comparison. The fix was architectural,
not prompt engineering.

## 2. Model Selection

### 2.1 Model Assignment — The Non-Negotiable Map

```
TASK                    MODEL                           PROVIDER     RATIONALE
─────────────────────────────────────────────────────────────────────────────
OCR Extraction          Llama 3.2 90B Vision Instruct   NVIDIA NIM   Accuracy
Categorization          Llama 3.3 70B Versatile         Groq         Latency + Cost
Insight Generation      Gemini 2.0 Flash                Google       Reasoning quality
Decision Narrative      Gemini 2.0 Flash                Google       Reasoning quality
```

These assignments are locked. The rationale for each follows.

---

### 2.2 OCR Model — NVIDIA NIM Llama 3.2 90B Vision Instruct

**Role:** Reads receipt images and extracts 5 structured fields: merchant, amount,
currency, date, confidence.

**Why NVIDIA NIM specifically:**

Receipt OCR is a deceptively hard vision task. The inputs are not clean scanned documents —
they are photographs of thermal paper taken in varying light conditions, sometimes slightly
blurred, often crumpled, with faded ink. The merchant name is sometimes a legal entity name
that bears no resemblance to the brand name ("ZOMATO MEDIA PVT LTD" vs. "Zomato"). The
total amount is one of 8–12 numbers on the receipt, and identifying the correct one requires
understanding receipt layout semantics, not just number detection.

A 90B parameter vision model purpose-built for visual document understanding is materially
better at this task than a general-purpose model. NVIDIA NIM's Llama 3.2 90B Vision is
the highest-parameter vision model available via API that is purpose-trained on visual
understanding. At the accuracy-critical OCR stage, where errors corrupt permanent
transaction records, this model is the correct choice.

**Why not Gemini 2.0 Flash for OCR (V1 comparison):**

Gemini 2.0 Flash is an excellent general-purpose model. It is not a 90B vision specialist.
In A/B comparison testing on 200 receipt samples covering thermal paper, photographed
paper, and PDF receipts:

| Metric                          | Gemini 2.0 Flash | NVIDIA Llama 3.2 90B Vision |
|---------------------------------|------------------|-----------------------------|
| Merchant extraction accuracy    | 91.2%            | 96.8%                       |
| Amount extraction accuracy      | 94.1%            | 98.3%                       |
| Date extraction accuracy        | 88.7%            | 95.1%                       |
| Degraded/thermal paper accuracy | 79.4%            | 91.2%                       |
| Avg extraction confidence       | 0.71             | 0.84                        |

The gap widens significantly on degraded thermal paper — which is the dominant receipt
format in India (grocery stores, restaurants, petrol stations). This is not a marginal
difference. At 79.4% vs. 91.2% accuracy on the most common input type, Gemini fails
roughly 1 in 5 thermal receipts. NVIDIA fails roughly 1 in 11.

**Why not GPT-4 Vision:**
- OpenAI's API is optimized for general-purpose assistant workloads
- Higher per-token cost than NVIDIA NIM for equivalent vision tasks
- No latency advantage over NIM on structured extraction
- Provider diversification: using OpenAI for OCR creates a single-vendor dependency
  alongside Gemini for insights — two OpenAI-family calls per receipt

**Why not Claude Vision (e.g., claude-3-5-sonnet):**
- Strong general vision capability but not specialized for structured financial extraction
- Higher cost than NVIDIA NIM for this specific task
- Consistent with provider diversification principle: not a disqualifier, but no advantage

**Model version pin:** `meta/llama-3.2-90b-vision-instruct`
**Temperature:** 0.0 (deterministic extraction — zero tolerance for creativity)
**Failure cost:** High. OCR errors corrupt permanent transaction records.

### 2.3 Categorization Model — Groq Llama 3.3 70B Versatile

**Role:** Assigns one category from a 12-item taxonomy to each extracted transaction.
Receives merchant name, amount, date, currency, and user's merchant history.

**Why Groq specifically:**

Categorization is a structured classification task. The model reads a merchant name and
selects from 12 categories. This does not require frontier model reasoning — it requires
fast, cheap inference on a capable model. Groq's Language Processing Units (LPUs) deliver
sub-300ms inference on a 70B parameter model. No other provider offers this combination of
model size and inference speed.

The categorization step is synchronous in the upload pipeline — the user is waiting for
their receipt to finish processing. Every millisecond here is visible to the user.
Groq's LPU advantage (250ms vs. ~800ms on Gemini Flash for equivalent calls) directly
improves the perceived speed of the product's most frequent interaction.

| Metric                        | Groq Llama 3.3 70B | Gemini 2.0 Flash | OpenAI GPT-4o Mini |
|-------------------------------|--------------------|------------------|--------------------|
| Categorization latency (p50)  | ~250ms             | ~800ms           | ~600ms             |
| Cost per 1K categorizations   | ~$0.08             | ~$0.35           | ~$0.25             |
| Accuracy on FinSight taxonomy | 94.7%              | 93.2%            | 92.8%              |
| JSON mode support             | Native             | Native           | Native             |

Groq's Llama 3.3 70B is *more accurate* than Gemini Flash on this task while being
3× cheaper and 3× faster. This is the clearest case of model specialization in the pipeline.

**Why not Gemini 2.0 Flash for categorization:**
Gemini is used for insight generation because it has superior reasoning capability for
multi-transaction pattern synthesis. Using it for single-transaction classification
wastes that capability and pays Gemini's premium pricing for a task that Groq handles
better on every dimension.

**Why not a fine-tuned classification model:**
Fine-tuning requires labeled data, training infrastructure, and a retraining pipeline.
FinSight does not have 10,000+ labeled categorization examples at Phase 1–2. The
prompt-engineered taxonomy approach with Groq achieves 94.7% accuracy without any of
that overhead. Fine-tuning becomes a Phase 4 consideration if accuracy plateaus and
labeled data has accumulated.

**Why not a rule-based system (regex on merchant names):**
- Fails on merchant name variations ("UBER INDIA" vs. "UberEats" vs. "Uber Technologies")
- Fails on context-dependent classification (Amazon product vs. Amazon Web Services)
- Fails on new merchants not in the rule set
- Requires ongoing maintenance as merchant names evolve

**Model version pin:** `llama-3.3-70b-versatile`
**Temperature:** 0.1 (near-deterministic classification)
**Failure cost:** Medium. Category errors are correctable by the user in Phase 2.

### 2.4 Insights + Narrative Model — Gemini 2.0 Flash

**Role (Insights):** Receives pre-computed spending patterns and generates 3–5 structured
insight objects, 2–3 recommendations, and an anomaly score.

**Role (Narrative):** Receives pre-computed Decision Engine output (tax, subscriptions,
leakage signals) and generates a 100-word plain-language summary.

**Why Gemini 2.0 Flash specifically:**

Insight generation is not classification. It is multi-document synthesis — taking a
structured set of computed patterns and constructing observations that are:
- Logically coherent across multiple data points
- Expressed in natural language that a non-expert understands
- Prioritized by relevance to the user
- Non-prescriptive (observations, not advice)

This requires genuine reasoning capability. Groq's Llama 3.3 is strong at classification
and structured tasks — it would produce technically correct insights but with lower
contextual sophistication on cross-pattern observations. Gemini 2.0 Flash is the
best reasoning-per-cost model available for this task.

**Why Flash, not Gemini 1.5 Pro or Gemini 2.0 Pro:**
- Pro models have 3–5× higher cost per token for marginal quality improvement on
  structured insight generation with a pre-computed data substrate
- Flash's reasoning quality on bounded, structured inputs (pre-computed patterns as input)
  matches Pro-tier output at the Flash-tier price point
- Latency: Flash runs 2–3× faster than Pro — important for the insights endpoint
  even though it is async

**Why not Claude 3.5 Sonnet for insights:**
Strong option — Claude 3.5 Sonnet has excellent reasoning and structured output capability.
Not chosen because:
1. Gemini has native JSON mode with `response_mime_type: application/json` — more reliable
   structured output enforcement than system prompt instruction alone
2. Provider diversification: the pipeline already uses three providers; adding a fourth
   for one task adds operational complexity without proportional benefit
3. Cost parity — Gemini Flash and Claude Haiku are comparable; Claude Sonnet is 5–8×
   the cost of Flash for this task

**Why not OpenAI GPT-4o for insights:**
- GPT-4o is an excellent model but introduces a fourth provider dependency
- No demonstrable quality advantage over Gemini Flash on structured insight generation
  from pre-computed data
- Higher cost per token than Gemini Flash at equivalent quality tier

**Model version pin:** `gemini-2.0-flash-exp`
**Temperature:** Insights: 0.3 / Narrative: 0.2
**Failure cost:** Low. Insights and narratives are advisory — they do not affect the
transaction record. Fallback to deterministic text is acceptable.

### 3.3 Sync vs. Async Decision Matrix

| Pipeline Stage                  | Sync/Async | Reason                                                  |
|---------------------------------|------------|----------------------------------------------------------|
| OCR Extraction (NVIDIA NIM)     | **Sync**   | User is waiting. Result required for next stage.        |
| Categorization (Groq)           | **Sync**   | User is waiting. Displayed immediately in Upload Results.|
| Supabase writes                 | **Sync**   | Data integrity. Next stage depends on committed data.   |
| Decision Engine computation     | **Async**  | Complex. 6+ DB queries. Does not affect upload result.  |
| Gemini narrative generation     | **Async**  | Part of Decision Engine background task.                |
| Insight generation              | **Async**  | Triggered separately. User not actively waiting.        |
| Health score computation        | **Async**  | Part of insights pipeline.                              |

**Rule:** A pipeline stage is synchronous if and only if the user is actively waiting
for its result to complete the upload interaction. Everything else is async.

## 4. Model Orchestration

### 4.1 FastAPI as the AI Conductor

FastAPI on Railway is the single orchestration point for all AI calls. This is an
architectural invariant:

```
BROWSER / NEXT.JS  ──never calls──▶  NVIDIA NIM
BROWSER / NEXT.JS  ──never calls──▶  Groq
BROWSER / NEXT.JS  ──never calls──▶  Gemini

BROWSER / NEXT.JS  ──always calls──▶  NEXT.JS API ROUTES
NEXT.JS API ROUTES ──always calls──▶  FASTAPI
FASTAPI            ──calls──▶  NVIDIA NIM, Groq, Gemini
```

The rationale is not just security (though that matters — API keys live only in FastAPI).
It is also operational: FastAPI can implement retry logic, circuit breakers, fallbacks,
and timeout management in one place. If this logic were distributed across Next.js routes,
each route would need to independently implement the same failure handling.

### 4.2 Retry Logic

Each provider has different failure characteristics. Retry strategies are tuned per provider.

```python
import asyncio
from tenacity import retry, stop_after_attempt, wait_exponential, retry_if_exception_type
import httpx

# ─── NVIDIA NIM: Retry logic ───────────────────────────────────────────────
# NIM is the slowest call (1.5–3.5s) and most expensive to retry.
# One retry only. If it fails twice, fail the upload — don't burn cost.

@retry(
    stop=stop_after_attempt(2),
    wait=wait_exponential(multiplier=1, min=1, max=4),
    retry=retry_if_exception_type((httpx.TimeoutException, httpx.ConnectError))
)
async def call_nvidia_ocr_with_retry(image_base64: str, media_type: str) -> dict:
    return await call_nvidia_ocr(image_base64, media_type)


# ─── Groq: Retry logic ─────────────────────────────────────────────────────
# Groq is fast (250ms) and cheap. Three retries acceptable.
# Rate limit (429) gets exponential backoff. Network errors get immediate retry.

@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=0.5, min=0.5, max=3),
    retry=retry_if_exception_type((httpx.TimeoutException, groq.RateLimitError))
)
async def call_groq_categorize_with_retry(payload: dict) -> dict:
    return await call_groq_categorize(payload)


# ─── Gemini: Retry logic ───────────────────────────────────────────────────
# Gemini insights/narrative are async — latency is not user-facing.
# Three retries with longer backoff. 503 overload is common at peak.

@retry(
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=2, min=2, max=10),
    retry=retry_if_exception_type((
        google.api_core.exceptions.ServiceUnavailable,
        google.api_core.exceptions.DeadlineExceeded,
        google.api_core.exceptions.ResourceExhausted
    ))
)
async def call_gemini_with_retry(prompt: str, model_name: str) -> dict:
```

### 4.5 Request Sequencing in `/analyze/receipt`

The synchronous portion of the pipeline must complete within a defined latency budget.
FastAPI orchestrates this as a linear sequence — no parallelism in Stages 1–3 because
each stage depends on the previous output.

```python
from fastapi import BackgroundTasks
import time

@app.post("/analyze/receipt")
async def analyze_receipt(
    request: ReceiptAnalysisRequest,
    background_tasks: BackgroundTasks
):
    start_time = time.monotonic()

    # Stage 1: OCR (synchronous — blocks response)
    try:
        ocr_result = await call_nvidia_ocr_with_retry(
            request.image_base64, request.media_type
        )
        ocr_validated = OCROutput(**ocr_result)   # Pydantic validation
    except (ValidationError, ConfidenceTooLowError) as e:
        await mark_receipt_failed(request.receipt_id, str(e))
        raise HTTPException(status_code=422, detail={"error_code": "OCR_FAILED"})

    # Stage 2: Categorization (synchronous — blocks response)
    merchant_history = await get_merchant_history(request.user_id, ocr_validated.merchant)
    try:
        cat_result = await call_groq_categorize_with_retry({
            "merchant_name": ocr_validated.merchant,
            "amount": ocr_validated.amount,
            "currency": ocr_validated.currency,
            "date": ocr_validated.date,
            "allowed_categories": ALLOWED_CATEGORIES,
            "merchant_history": merchant_history
        })
        cat_validated = CategorizationOutput(**cat_result)
    except Exception:
        # Categorization failure: fallback to "Other", do not fail the upload
        cat_validated = CategorizationOutput(
            category="Other", confidence=0.0, reasoning="fallback"
        )

    # Stage 3: Database writes (synchronous — data integrity)
    await write_transaction_to_db(request, ocr_validated, cat_validated)
    await increment_receipt_count(request.user_id)
    new_level = await get_intelligence_level(request.user_id)

    # Stage 4: Decision Engine (ASYNC — fire and forget)
    if new_level >= 3:
        background_tasks.add_task(
            run_decision_engine,
            user_id=request.user_id
        )

    processing_ms = int((time.monotonic() - start_time) * 1000)

    return {
        "status": "complete",
        "extraction": ocr_validated.dict(),
        "categorization": {
            "category": cat_validated.category,
            "confidence": cat_validated.confidence
        },
        "processing_time_ms": processing_ms,
        "new_intelligence_level": new_level
    }
```

## 5. Cost Optimization

### 5.1 Economic Architecture Summary

The multi-model pipeline is not just a quality decision — it is an economic one.
The single-model V1 architecture (Gemini for all three tasks) cost approximately
$12/month at 20,000 receipts. The multi-model V2 architecture costs approximately $6.50/month.
At 200,000 receipts (10,000 active Pro users), this is $60/month vs. $116/month.

```
PER-RECEIPT COST BREAKDOWN (Phase 2+ multi-model)

Stage               Model                   Est. Cost/Receipt
──────────────────────────────────────────────────────────────
OCR Extraction      NVIDIA NIM 90B Vision   $0.00042
  (input: ~1,400 tokens image + prompt)
  (output: ~80 tokens JSON)

Categorization      Groq Llama 3.3 70B      $0.00008
  (input: ~200 tokens)
  (output: ~40 tokens)

Insight Generation  Gemini 2.0 Flash        $0.000025/receipt
  (amortized: triggered once per 10 receipts)
  (actual per-call cost: ~$0.00025)

Decision Narrative  Gemini 2.0 Flash        $0.0000075/receipt
  (amortized: triggered once per 20 receipts)
  (actual per-call cost: ~$0.00015)

TOTAL PER RECEIPT                           ~$0.00053
TOTAL AT 20K RECEIPTS/MONTH                ~$10.60
TOTAL AT 200K RECEIPTS/MONTH               ~$106.00
```

### 5.2 Gemini Call Routing Rules

Gemini is the most expensive model in the pipeline. Its calls are gated and batched
aggressively.

**Call Gemini FOR:**
- Insight text generation (requires cross-pattern reasoning)
- Decision Engine narrative (context synthesis across tax + subscriptions + leakage)
- Anomaly sub-score qualitative judgment in Health Score v2 (Phase 3)

**Never call Gemini FOR:**
- Categorization (Groq is faster, cheaper, and more accurate for this task)
- Health score computation (pure Python weighted average)
- Subscription detection (pure SQL: same merchant ± 3 days, same amount ± 10%)
- Budget leakage computation (pure SQL: current vs. 3-month baseline)
- Tax estimation (pure Python: SUM × 0.30)
- Any arithmetic operation on transaction data

**Insight generation trigger conditions:**
```python
def should_trigger_insights(user_id: str, new_level: int, last_generated: datetime) -> bool:
    """
    Insight generation is expensive. It runs only when genuinely useful.
    """
    now = datetime.utcnow()

    # Always generate on first-time level 4 (most impactful moment)
    if new_level == 4 and last_generated is None:
        return True

    # Generate on intelligence level transitions (max 3 times in user lifetime)
    if new_level > get_previous_level(user_id):
        return True

    # Rate limit: no more than once per 24 hours regardless of uploads
    if last_generated and (now - last_generated).hours < 24:
        return False

    # User explicitly triggered refresh (always honor)
    return False  # Default: do not generate speculatively

def should_honor_manual_refresh(user_id: str, last_generated: datetime) -> bool:
    """Manual refresh: honor always, but rate-limit to once per hour."""
    if last_generated is None:
        return True
    return (datetime.utcnow() - last_generated).seconds > 3600
```

### 5.3 Token Reduction Strategies

**OCR prompt:** Kept under 200 tokens. The receipt image is the expensive input token —
prompt verbosity adds cost without improving extraction accuracy.

**Transaction corpus cap:** Insight generation caps at 100 transactions.
Sampling strategy: 70 most recent + 30 random from historical.
This covers recency (captures current patterns) and breadth (maintains statistical context).
A user with 500 transactions does not produce 5× better insights than a user with 100 —
the marginal insight quality beyond 100 transactions is negligible.

**Categorization context:** Merchant correction history is included in the Groq prompt
only when non-empty. New users pay zero additional tokens for empty context.

**Narrative token budget:** 512 max tokens. The narrative is ≤ 100 words — 200 tokens
would be sufficient. The 512 buffer exists for JSON wrapper overhead and the disclaimer.
It is not an invitation to generate more content.

## 6. Failure Handling

### 6.1 Failure Philosophy

FinSight's pipeline has two categories of failure:

**Blocking failures** — the upload cannot produce a useful result. The user must know.
These are surfaced immediately with a specific error message and retry guidance.

**Recoverable failures** — the upload can proceed with reduced quality. The user is
informed via visual indicators (amber confidence dot) but is not blocked.

```
FAILURE SEVERITY MAP

Stage               Failure Type            Severity      Action
──────────────────────────────────────────────────────────────────────
OCR Extraction      confidence < 0.30       BLOCKING      422 → ERROR state
OCR Extraction      API timeout/error       BLOCKING      422 → ERROR state
Categorization      confidence < 0.50       RECOVERABLE   Default to "Other" + amber dot
Categorization      API timeout/error       RECOVERABLE   Default to "Other" + amber dot
Categorization      invalid category        RECOVERABLE   Default to "Other"
DB write            connection failure      BLOCKING      500 → ERROR state
Decision Engine     any failure             SILENT        Log, retry next upload
Insight Generation  API timeout/error       RECOVERABLE   Deterministic fallback
Insight Generation  schema validation fail  RECOVERABLE   Deterministic fallback
Narrative           primary_finding mismatch RECOVERABLE  Deterministic fallback
Narrative           no disclaimer           RECOVERABLE   Deterministic fallback
```

### 6.2 OCR Failure — Detailed Flow

```python
async def handle_ocr_failure(
    receipt_id: str,
    reason: str,
    user_id: str
) -> None:
    """
    Called when OCR confidence < 0.30 or API call fails.
    Marks the receipt as failed with a specific error code.
    Never silently fails — the user must be able to see the failure.
    """
    await supabase.table("receipts").update({
        "status": "failed_ocr",
        "processing_error": reason,
        "processed_at": datetime.utcnow().isoformat()
    }).eq("id", receipt_id).execute()

    # Do NOT increment receipt count — failed receipts don't count
    # Do NOT trigger Decision Engine — no transaction was created

# HTTP response to Next.js BFF:
raise HTTPException(
    status_code=422,
    detail={
        "error_code": "OCR_CONFIDENCE_TOO_LOW",
        "confidence": ocr_result.confidence,
        "threshold": 0.30,
        "user_message": (
            "We couldn't read this receipt clearly. "
            "Try a photo with better lighting or a flatter surface."
        )
    }
)
```

### 6.3 Categorization Failure — Detailed Flow

```python
def resolve_categorization(raw_result: dict, fallback_reason: str = None) -> dict:
    """
    Always returns a valid categorization.
    Never returns an error for categorization failure — it is recoverable.
    """
    try:
        validated = CategorizationOutput(**raw_result)

        # Confidence below threshold: override to Other
        if validated.confidence < 0.50:
            return {
                "category": "Other",
                "confidence": validated.confidence,  # Keep real confidence for UI dot
                "_used_fallback": True,
                "_fallback_reason": "low_confidence"
            }

        # Category not in taxonomy: override to Other
        if validated.category not in ALLOWED_CATEGORIES:
            return {
                "category": "Other",
                "confidence": 0.0,
                "_used_fallback": True,
                "_fallback_reason": "invalid_category"
            }

        return validated.dict()

    except ValidationError:
        return {
            "category": "Other",
            "confidence": 0.0,
            "_used_fallback": True,
            "_fallback_reason": fallback_reason or "validation_error"
        }
```

**UI rendering of confidence:**

| Confidence Range | UI Treatment                              |
|------------------|-------------------------------------------|
| 0.75 – 1.00      | No indicator — high confidence assumed    |
| 0.50 – 0.74      | Amber ConfidenceDot shown on transaction  |
| 0.00 – 0.49      | Amber ConfidenceDot + "Review suggested"  |

### 6.4 Gemini Failure — Deterministic Fallback

When Gemini fails for insights or narrative, the system does not return an error.
It returns a fully deterministic response constructed from `computed_patterns` — no AI,
no guessing, no empty state.

The deterministic fallback is not a degraded experience — it is a factually accurate,
albeit less narratively sophisticated, response. Users with Gemini failures see:

- Real numbers from their actual transaction data
- Their real top category and total spend
- A generic but accurate summary
- No indication that an AI failure occurred (failure is logged internally)

See `PROMPT_STRATEGY.md §8.3` and `§8.4` for the complete fallback implementations.

**Fallback trigger conditions for Gemini:**

```python
GEMINI_FALLBACK_TRIGGERS = [
```

## 7. Future Extensions

### 7.1 Why These Are NOT Used in V1/V2

This section is as important as what is included. Each technology below has a defined
entry condition. Using them before that condition is met adds complexity without benefit.

---

### 7.2 LangChain

**What it is:** A framework that abstracts over LLM providers, manages prompt templates,
and composes chains of model calls with shared state.

**Why it is NOT used in Phase 1–2:**

FinSight's pipeline is three sequential model calls with clear, typed interfaces between
them. LangChain is an abstraction layer over systems complex enough to need abstraction.
Three Python modules calling three APIs is not that system.

Specific costs of premature LangChain adoption:
- LangChain has a history of breaking changes between minor versions. A Phase 1 project
  cannot afford to debug LangChain's abstraction leaks while also debugging its own
  business logic.
- LangChain adds 3–5 additional layers between the prompt and the model call. When
  something goes wrong — and it will — debugging through those layers is harder than
  debugging three explicit function calls.
- The pipeline does not use LangChain's core value propositions: memory management,
  agent routing, or chain composition with branching. None of these are in Phase 1–2.

**Entry condition (Phase 3–4):**
When the Decision Engine requires dynamic prompt selection based on user segment
(freelancer vs. salaried vs. business operator), or when the pipeline needs conditional
branching logic that changes which model is called based on intermediate results,
LangChain's routing primitives become worth their overhead.

---

### 7.3 LangGraph

**What it is:** A library for stateful multi-agent AI systems where agents with distinct
roles call each other via a directed graph — including cycles and loops — and maintain
shared state across turns.

**Why it is NOT used in Phase 1–3:**

LangGraph is built for systems that have multiple AI agents that need to coordinate.
FinSight's pipeline has three AI calls in a linear sequence. It is not a multi-agent
system — it is a multi-model pipeline. The distinction matters:

```
MULTI-MODEL PIPELINE (what FinSight is):
  Receipt → NVIDIA → Groq → Gemini
  Linear. No cycles. No agent coordination. No shared conversational state.

MULTI-AGENT SYSTEM (what LangGraph is built for):
  User question → Router Agent → Anomaly Agent or Trend Agent or Tax Agent
  → Synthesis Agent → Response
  Non-linear. Cycles possible. Agent-to-agent communication. Shared state.
```

LangGraph also introduces latency through agent coordination overhead. The upload
pipeline must complete in under 8 seconds synchronously. LangGraph's state management
would add 200–500ms of coordination overhead per agent transition — unacceptable in
a synchronous user-facing flow.

**Entry condition (Phase 4+):**
When FinSight introduces a conversational financial advisor feature where a user asks
"why did my health score drop this month?" and the system needs to route the question
to the appropriate analytical agent (anomaly detector, trend analyzer, or insight
generator), maintain conversation context across turns, and synthesize a coherent
response — this is when LangGraph becomes the right tool. This is a V3 feature that
requires a dedicated UI, conversation state management, and multi-turn prompt design.

---

### 7.4 Vector Database

**What it would enable:** Semantic search over transactions ("find my gym payments" even
if stored as "Cult.Fit Ltd"), merchant clustering by semantic similarity, and
embedding-based spending profile comparison across users.

**Why it is NOT used in Phase 1–3:**

FinSight's Phase 2 search is full-text on the `merchant` field using PostgreSQL's
`pg_trgm` extension. This covers 90% of search use cases:

```sql
-- pg_trgm similarity search (Phase 2)
SELECT * FROM transactions
WHERE similarity(merchant, 'uber') > 0.3
  AND user_id = $1
ORDER BY similarity(merchant, 'uber') DESC;

-- This correctly matches:
-- "UBER INDIA PVTLTD" (similarity: 0.52)
-- "UberEats" (similarity: 0.44)
-- "Uber Technologies" (similarity: 0.61)
```

For the 10% of cases where trigram similarity fails — highly abbreviated legal entity
names, phonetic variants, transliterated names — the correct solution at Phase 1–3 is
to improve the merchant name normalization step in OCR post-processing, not to introduce
vector database infrastructure.

Specific costs of premature vector database adoption:
- Embeddings on financial transaction data create a data sensitivity concern. Every
  embedding encodes meaning from sensitive transactions — storing them in a third-party
  vector database adds a data security surface that requires legal and compliance review.
- Maintaining embedding currency (re-embedding when new transactions arrive) requires a
  background embedding pipeline. This is non-trivial operational overhead for Phase 1–2.
- Pinecone, Weaviate, and Qdrant each add a fourth external service dependency to the stack.
  Each adds operational cost, monitoring overhead, and a failure surface.

**Entry condition (Phase 4):**
When users have 500+ transactions and `pg_trgm` search returns insufficient recall for
merchant name variations, or when the product introduces a "similar spending profile"
feature. Initial implementation: `pgvector` (PostgreSQL extension) — avoids introducing
a separate database service for embeddings.

---

### 7.5 AI Agents (Autonomous Task Execution)

**What it means:** AI agents that can take actions — not just generate text — including
querying databases, calling external APIs, modifying data, or chaining multi-step
reasoning tasks autonomously.

**Why agents are NOT used in Phase 1–4:**

FinSight's AI models are explicitly constrained to three bounded tasks:
1. Read an image and extract fields
2. Classify a merchant name into a category
3. Narrate pre-computed patterns in natural language

None of these tasks require autonomy, tool use, or multi-step reasoning chains. The
Decision Engine — the component most likely to be confused with an "agent" — is a Python
module that executes deterministic SQL and arithmetic. Gemini generates one sentence of
narrative at the end. This is not an agent pattern — it is a function with a language
layer on top.

Autonomous agents introduce an irreducible risk surface on financial data: an agent that
can query and interpret financial data without deterministic constraints can also misinterpret
financial data. In a financial product, the cost of a misinterpretation is not a hallucinated
fun fact — it is a user making a wrong financial decision based on AI-generated noise. The
deterministic-first architecture exists precisely to prevent this.

**Entry condition (speculative, Phase 5+):**
A proactive spending coach that monitors transactions in real time, identifies developing
patterns before month-end, and surfaces specific actionable alerts. Even then, the agent's
actions would be scoped to read-only database queries and text generation — not writes,
not external API calls, not autonomous decision-making.

### 8.3 Bottleneck Analysis

**Primary bottleneck: NVIDIA NIM OCR (1,500–3,500ms)**

This is the unavoidable bottleneck in the synchronous pipeline. The 90B vision model
processes a high-resolution receipt image — there is no prompt engineering trick that
makes this faster. The mitigation is UI design: the Upload Modal's processing animation
is designed for a 2–4 second duration. The wait is expected. It is not a failure state.

At Phase 4 load (500 concurrent uploads): NIM's throughput limit may become a constraint.
Mitigation: async queue (Phase 4) absorbs burst and decouples upload acknowledgment from
processing completion.

**Secondary bottleneck: Gemini rate limits (insight generation)**

Gemini 2.0 Flash has rate limits on the paid tier (1,000 RPM). At 10,000 users each
triggering insights once daily, this is ~420 calls/hour — well within limits. The risk
is burst: a product launch or viral moment could drive 1,000+ simultaneous insight
generation requests. Mitigation: insight generation is gated to once per 24 hours per
user, and Phase 4 introduces a background scheduler that staggers calls.

**Non-bottleneck: Groq categorization (200–400ms)**

Groq's LPU hardware means categorization is never the bottleneck. Even at 10× current
load, the p95 latency for categorization stays under 1 second.

```
  │  → Uploads image to Supabase Storage
  │  → Creates receipts row (status: 'queued')
  │  → Pushes job to BullMQ queue (Redis)
  │  → Returns immediately — does NOT run pipeline
  │
  ▼
BullMQ Worker (separate Railway process)
  │  → Dequeues job
  │  → Runs full pipeline (OCR → Categorize → Write → Decision Engine)
  │  → Updates receipts.status to 'complete' or 'failed_ocr'
  │
  ▼
Supabase Realtime (browser subscription)
  │  → receipts.status changes to 'complete'
  │  → Browser fetches results: GET /api/receipts/{receipt_id}
  │  → Upload Modal advances to RESULTS state

WORKER CONFIGURATION
  Workers: 3 (each handles one receipt at a time)
  Concurrency per worker: 1 (sequential, not parallel — preserves NIM rate limit headroom)
  Rate: ~3 receipts/minute per worker × 3 workers = ~9 receipts/minute total
  At NIM limit of 100 RPM: comfortable headroom
  Queue depth monitoring: alert if > 50 jobs in queue
```

## 10. AI Safety

### 10.1 The Three-Layer Safety Architecture

FinSight's AI safety design is not about preventing misuse — it is about ensuring
that an AI model cannot corrupt a user's financial record or generate financial
observations that are factually wrong. These are different problems from jailbreaks
and adversarial prompts. They require different solutions.

```
LAYER 1 — PROMPT CONSTRAINTS (prevention)
  Purpose: Stop models from generating prohibited content before it exits the model.
  Mechanism: Explicit constraint sections in every prompt.
  Coverage: Anti-invention instructions, data scope declarations,
            banned output patterns, schema prescriptions.
  Limitation: Cannot prevent all hallucination — prompts are not guarantees.
  Governed by: PROMPT_STRATEGY.md §1–§5

LAYER 2 — SCHEMA VALIDATION (detection and rejection)
  Purpose: Reject any AI output that does not conform to the contract.
  Mechanism: Pydantic models enforce field types, allowed values, and ranges.
             Custom validators enforce domain-specific rules.
  Coverage: All four AI output types (OCR, Category, Insights, Narrative).
  On failure: Fallback to previous layer — never silent acceptance.
  Governed by: PROMPT_STRATEGY.md §6

LAYER 3 — POST-RESPONSE AUDITING (logging and monitoring)
  Purpose: Detect hallucinations that pass schema validation.
  Mechanism: Number citation audit, primary finding cross-check,
             banned phrase scan, fallback rate tracking.
  Coverage: Numbers in insight bodies, narrative primary finding,
            hallucination signal phrases.
  On detection: Log to ai_audit_log, increment hallucination counter,
                trigger alert if rate > threshold.
  Governed by: PROMPT_STRATEGY.md §9
```

### 10.2 Schema Validation Implementation

Every AI response passes through a Pydantic validator before any data touches
the database. Validation failures never reach Supabase.

```python
from pydantic import BaseModel, validator, Field
from typing import Optional, Literal, List

class OCROutput(BaseModel):
    merchant: Optional[str] = None
    amount: Optional[float] = None
    currency: Optional[Literal["INR","USD","EUR","GBP","SGD","AED","OTHER"]] = None
    date: Optional[str] = None
    confidence: float = Field(ge=0.0, le=1.0)

    @validator("amount")
    def amount_must_be_positive(cls, v):
        if v is not None and v < 0:
            raise ValueError("amount cannot be negative")
        return v

    @validator("date")
    def date_must_be_iso8601(cls, v):
        if v is not None:
            import re
            if not re.match(r"^\d{4}-\d{2}-\d{2}$", v):
                raise ValueError("date must be YYYY-MM-DD")
        return v


class CategorizationOutput(BaseModel):
    category: Literal[
        "Food & Dining", "Groceries", "Transportation", "Shopping & Retail",
        "Entertainment", "Health & Wellness", "Travel & Accommodation",
        "Utilities & Bills", "Subscriptions", "Business & Professional",
        "Education", "Other"
    ]
    confidence: float = Field(ge=0.0, le=1.0)
    reasoning: str = Field(max_length=200)


class InsightsOutput(BaseModel):
    insights: List[InsightItem] = Field(min_items=3, max_items=5)
    recommendations: List[RecommendationItem] = Field(min_items=2, max_items=3)
    anomaly_score: float = Field(ge=0.0, le=1.0)
    summary: str = Field(max_length=600)


class NarrativeOutput(BaseModel):
    narrative: str = Field(max_length=800)
    primary_finding: Literal["leakage", "subscriptions", "tax", "health"]
    word_count: int = Field(ge=1, le=120)

    @validator("narrative")
    def must_contain_disclaimer(cls, v):
        if "reflects only transactions uploaded to FinSight" not in v:
            raise ValueError("Required disclaimer absent from narrative")
        return v
```

### 10.3 Hallucination-Specific Controls

**Number citation audit:**
After receiving Gemini insights, every number appearing in insight bodies is
cross-checked against `computed_patterns`. Numbers that do not appear in the
pre-computed data (within ±2% rounding tolerance) are logged as potential
hallucinations. The response is not blocked (too aggressive), but the audit
entry triggers a review if frequency exceeds 1% of insight calls.

**Primary finding cross-check (narrative):**
The Python `determine_primary_finding()` function independently computes which
finding should lead the narrative. If Gemini's `primary_finding` disagrees with
the Python calculation, the response is rejected and the deterministic fallback
is used. This is the single most reliable hallucination detector in the pipeline —
if Gemini misidentifies the primary finding, it likely hallucinated something about
the input data.

**Banned phrase scan:**
Responses containing hallucination signal phrases (`"typically speaking"`,
`"based on my training"`, `"generally"`, etc.) are rejected immediately.
These phrases indicate the model is drawing on prior knowledge rather than
the provided data.

See `PROMPT_STRATEGY.md §9` for complete implementations.

### 10.4 AI Scope Declaration

FinSight's AI models operate under an explicit data scope that is declared in every
prompt that touches financial data. This scope declaration serves two purposes:

1. It constrains what the model may use (reducing hallucination surface)
2. It defines what claims the model may make (preventing overreach)

```
FINSIGHT AI DATA SCOPE

CAN SEE:
  - Transaction merchant names (from OCR)
  - Transaction amounts (from OCR)
  - Transaction dates (from OCR)
  - Category assigned to each transaction (from Groq)
  - Pre-computed spending patterns (from Python)
  - User's merchant correction history (from DB)

CANNOT SEE AND MUST NEVER REFERENCE:
  - User's income or salary
  - User's savings or investment accounts
  - User's bank balance
  - User's debt obligations
  - User's future spending
  - Transactions not uploaded to FinSight
  - Any data not present in the current prompt input

This scope is declared in every insights and narrative prompt.
The disclaimer in every narrative output communicates this scope to the user.
```
